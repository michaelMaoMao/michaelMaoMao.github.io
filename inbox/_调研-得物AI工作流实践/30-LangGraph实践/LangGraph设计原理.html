Building LangGraph: Designing an Agent Runtime from first principles（设计原理精读）

本文是 LangChain 官方对 LangGraph 设计哲学的”自述”，是理解为何得物等企业选择 LangGraph 作为生产级 agent 编排引擎的一手资料。原文作者 Nuno Campos，发布于 2025-09-04，同步 LangGraph 1.0 alpha。

一、为什么需要再造一个框架

LangChain 团队从原 langchain 库（2022 发布）收到的核心反馈是：“上手容易，但难以定制和扩展到生产”。两年多前重启 LangGraph 时，团队把目标定死在一条：“这就是你用来在生产环境跑 agent 的框架”，凡有 tradeoff 一律优先生产可用性而非”入门体验”。

1.1 Agent 与传统软件的三个关键差异

团队通过自建 agent、并与 Uber / LinkedIn / Klarna / Elastic 等公司合作，把 agent 的特殊性收敛为三条：

  1. 更高的延迟，更难留住用户——backend 接口过去以毫秒计，现在 agent 一次运行要数秒、数分钟、未来甚至数小时。LLM 本身慢、且越来越慢（test-time compute）；多步循环与链式 prompt 进一步放大；非 LLM 步骤（取数、guardrails、verifiers）也叠加在前后。
  2. 长任务失败重试代价高昂——传统软件 bug 直接 retry；agent 在第 9 分钟失败、回到起点重跑，既费时又烧钱。
  3. LLM 的非确定性——输入和输出都是开放的，开发期测试无法覆盖用户和 LLM 的所有”惊喜”组合。

1.2 从差异到六大必备特性

差异 衍生需求 LangGraph 提供的特性
延迟 缩短实际延迟 Parallelization（并行化，且无数据竞争）
延迟 缩短感知延迟 Streaming（流式，token 级 / step 级 / 进度条）
可靠性 减少重试次数 Task queue（任务队列，解耦请求与执行）
可靠性 降低单次重试成本 Checkpointing（检查点，保存中间快照）
非确定性 与用户协作 Human-in-the-loop（中断/恢复/审批/time travel）
非确定性 观测与调优 Tracing（轨迹、输入、输出全程可观测）

作者明确说：如果你的 agent 不需要这 6 个特性中的大多数（例如单 prompt、无工具、很短），那你可能既不需要 LangGraph 也不需要任何框架。

此外，团队意识到开发者不会为这 6 项特性付出额外延迟（尤其 chatbot 场景），因此 “低延迟”成为贯穿性约束。

二、为什么不复用已有框架

候选 否决理由
DAG 框架（Airflow 等） 名字即问题——LLM agent 需要循环（cycles），DAG 算法天然不支持
Durable execution engines（Temporal 等） 设计早于 LLM agent，缺 streaming；步骤间引入 chatbot 可感的延迟；历史越长性能越退化——这对越来越长、越来越复杂的 agent 是个糟糕的赌注

结论：LLM 足够不同，需要给既有生产基础设施注入新思想，于是开建 LangGraph。

三、核心设计哲学（两大原则）

LangGraph 全部设计决策由两条原则驱动，这也是它区别于”抽象当道”的同类框架的根本：

原则一：我们不知道 AI 的未来

对未来做的假设越少越好。 唯一愿意固化的假设只有那三条本质认知：LLM 是 slow、flaky、open-ended 的。除此之外一律不假设，以保证框架在 1/2/3 年后仍然 relevant。

原则二：用起来应该像在写普通代码

公开 API 尽量贴近”无框架代码”。对开发者代码施加的每一个要求，都必须由一个足够高价值的特性来证明其合理性，否则”跳过框架、直接裸写”的吸引力太大——任何框架最大的对手永远是”不用框架”。

这两条原则落地的两个关键决策

  1. Runtime 与 Developer SDK 解耦

    • Runtime（PregelLoop）：实现 6 大特性、规划计算图、执行。可独立演进、做性能优化、试验激进改动（如分布式执行）而不影响上层 API。
    • SDK：目前两套——StateGraph 与 imperative/functional API。已成功引入 imperative SDK、废弃最早的”无共享状态的 Graph 接口”。

  2. 6 大特性都是 opt-in 的积木
    开发者按需取用。例如 interrupt() 函数——human-in-the-loop 能力在你调用它之前完全不挡路。这让 LangGraph 成为低层级框架，在一片鼓吹”高级抽象”的同行中独树一帜。

四、执行模型：Channels / Nodes / Execution Loop

这是 LangGraph 最底层、最关键的架构设计——结构化、离散步骤（structured agents with discrete steps） 是其他一切（checkpointing、HITL）的基石。

4.1 为什么必须”结构化”

单函数 + 一个大 while 循环固然可以写 agent，但你会失去 checkpointing 和 human-in-the-loop 的能力——因为（Python 生成器等）子例程的执行状态无法以可移植格式序列化、跨机器跨时间恢复。一旦把 agent 拆成多个离散步骤，就为持久化、中断、恢复打开了大门。

4.2 执行算法：基于 BSP/Pregel

团队否决了”无算法”（早期 precursor 出现并发节点非确定性 bug），也否决了 DAG 算法（不支持循环），最终选中 BSP / Pregel 算法，因为它提供确定性并发 + 完整支持循环。

4.3 三个核心抽象

抽象 定义
Channel（通道） 持有数据（任意 Python/JS 类型），有 name 和当前 version（单调递增字符串）
Node（节点） 待执行的函数，订阅一个或多个 channel，channel 变化时触发执行
Input / Output channel 若干 channel 映射为输入（写入起始值即触发订阅节点）和输出（执行停止时这些 channel 的值即返回值）

4.4 执行循环（每个 iteration）

停止条件：没有更多 node 可跑（所有 node 都已看到订阅 channel 的最新 version），或达到开发者设置的最大迭代步数。

五、六大特性如何在执行模型上落地

特性 实现要点
Parallelization 算法天生为”无数据竞争的并行”而设计；依赖允许时自动并行；各节点独立 state 副本；更新应用顺序不依赖谁先开始/结束——保证执行顺序与延迟波动不影响最终输出（这对非确定性 LLM 尤其重要，使输出变异永不归咎于框架）
Streaming 结构化执行天然提供更多中间输出点；执行引擎无需开发者写额外代码即可在 node 内部与 step 边界收集流式输出；共 6 种 stream mode：values / updates / messages / tasks / checkpoints / custom（chatbot 用 messages，长跑 agent 用 updates）
Checkpointing 保存的是序列化的 channel values（默认 MsgPack，可选加密）+ version strings + 每个 node 最近看到的 channel version 记录；可跨机器、跨任意时间恢复，不依赖某台机器上进程还活着
Human-in-the-loop 复用同一套 checkpointing 实现”预期中断”；比”保持 agent 运行等输入”强——后者在时间（等几个月）和规模（大量并发中断）上都无法 scale
Tracing 结构化步骤让 agent 进度清晰可查；原生集成 LangSmith（首代 LLM 观测平台）、LangGraph Studio（运行时调试），并可发 OTEL traces
Task queue 超出 Python 库范畴，由 LangGraph Platform 提供

六、性能画像（Linear / Constant Scaling）

作者强调：可靠性不能以延迟为代价。LangGraph 在 agent 的所有”尺寸变量”上扩展得非常优雅——这对”agent 越来越长、步数越来越多、状态越来越大”的未来是极好的位置。

6.1 关键尺寸变量

  • node 数、edge 数、channel 数
  • 单步活跃 node 数
  • 调用历史长度（本次调用已执行的 step 数）
  • thread 数（不同输入/上下文的独立调用）

6.2 一次调用的四个动作及其复杂度

动作 含义 关键结论
Starting invocation 从存储拉最新 checkpoint 并反序列化 对 node/channel 是 O(n)，对 history 长度是 O(1)（只取最新 checkpoint，不重放历史），对 thread 数 O(1)
Planning a step 决定下一步跑哪些 node、准备输入 对 node 数 O(1)（上一步存了 updated channels 列表，无需遍历所有 node），对 history O(1)
Running a step 执行各 node 代码 对 node 总数 O(1)（只影响本步活跃 node），对 active nodes 线性
Finishing a step 应用 channel 更新、bump version、存 checkpoint 对 node/channel 线性，对 history 长度 O(1)

最关键的一点：所有动作对”调用历史长度”都是 O(1)。这与 durable execution engines（性能随历史退化）形成鲜明对比，是作者押注的核心赌注之一。

七、核心设计目标总结

Control（控制）：agent 严格按你的意图执行——通过结构化、确定性并发的执行模型保证输出变异不归咎于框架，并让你能在任意点插入审批/中断/time travel。

Durability（持久化/可靠）：长跑、慢、flaky 的 LLM agent 也能在生产中可靠运行——通过 checkpointing（跨机器跨时间恢复）、task queue（可靠重试）、tracing（全程可观测）实现。

调研笔记

这篇文章如何解释得物的技术选型

得物 AI 工作流实践中选择 LangGraph 作为编排引擎，本文给出了一手的设计依据，关键对应点如下：

  1. interrupt / resume 的底层支撑
    得物方案中强调的”中断/恢复”能力，本文揭示它不是临时实现的特性，而是 LangGraph 执行模型（structured + checkpointing）的自然产物——checkpoint 序列化了 channel values + version，可以跨机器、跨任意时间恢复。这解释了为什么得物可以放心地基于 LangGraph 做长流程审批、人工介入。

  2. 为什么是 LangGraph 而非自研编排
    本文第 2 节明确否决了 DAG 框架（不支持循环）和 Temporal 类 durable engine（无 streaming、历史越长越慢）。得物的工作流天然有循环（重试、迭代），且对延迟敏感（用户体验），LangGraph 的 BSP/Pregel + 对 history O(1) 正好命中痛点。

  3. “编排引擎”定位而非”agent 框架”
    得物把 LangGraph 当编排层，自己在上层做业务节点——这正好踩中 LangGraph 的”低层级框架”哲学（原则二：像写普通代码，6 大特性 opt-in）。作者原话：”LangGraph remaining relevant, so we’re happy with our approach“——低抽象换来了长期适用性。

  4. 生产级 agent 的关键考量清单
    本文的 6 大特性（Parallelization / Streaming / Task queue / Checkpointing / HITL / Tracing）可以直接作为得物方案”为什么需要 LangGraph”的论证矩阵——每一条都对应生产中的真实痛点。

  5. Control + Durability 作为选型口号
    得物对外讲”可靠、可控”时，可以直接引用本文的定义：control = 结构化执行保证意图不跑偏；durability = checkpoint + queue + tracing 让慢/flaky 的 agent 也能稳定上线。
