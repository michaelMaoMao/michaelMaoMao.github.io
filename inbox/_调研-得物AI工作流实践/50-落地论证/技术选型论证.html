技术选型论证

核心问题：得物用了 LangGraph + Dify，我要落地类似实践，该选哪个？答案不是”选一个”，而是”按场景选”。

三、得物的选型逻辑（关键启示）

得物不是”选一个统一引擎”，而是”按场景特性选”：

场景特性 选型 理由
需要可控状态机 + 人机中断 LangGraph interrupt/resume、checkpoint、HITL
需要 Skill 资产化 + 自学习 Hermes Skills 自主创建自优化（Learning Loop）
需要省事快速搭建 ReAct Spring AI 框架内置循环 + 工具拦截器
需要快速可视化验证 Dify 低代码，非技术可参与

启示：没有银弹，按场景选。但有一个共性——都遵循”确定性机制锁定 + 模型只做语义”的铁律（路由用代码、计算用代码、感知用模型）。

四、针对你的项目的推荐

假设：你要落地一套可控的 AI 工作流（有业务约束、需要人确认、要扩展）。

推荐路径：Dify 验证 → LangGraph 生产

这是得物验证过的路径，风险最低：

  1. 第 0 步：用 Dify 快速搭原型，验证”AI 能否完成核心任务”（得物第一版）
  2. 第 1 步：原型跑通后，用 LangGraph 重写为生产级（得物第二版）
  3. 第 2 步：如需 Agent 自学习沉淀，引入记忆/Skill 系统（参考得物自进化文章）

为什么 LangGraph 是”可控工作流”的默认选择

  1. interrupt/resume 原生支持 — 人机协作刚需
  2. Checkpointer 持久化 — 中断恢复（关浏览器再开能继续）
  3. 代码级灵活度 — 复杂业务约束（得物 16+ 组件模块协议）
  4. 生态成熟 — LangChain 团队，MIT 开源，文档全
  5. 对历史 O(1) — 长任务不退化（对比 Temporal 类）

何时不该选 LangGraph

  • 只是验证想法、非技术人要参与 → Dify 更快
  • 不需要 HITL/持久化、就是简单 ReAct → Spring AI 更省事
  • 核心诉求是 Agent 自我进化沉淀技能 → Hermes 或自建记忆系统
  • 避免一上来就 LangGraph（过度工程，想法未验证）

五、选型反模式（得物踩过的坑）

反模式 问题 得物的修正
第一版直接上复杂架构 组件硬编码、无持久化、不可逆 先 Dify 验证范式
用 Dify 做生产级复杂编排 灵活度不够，无法 Capability Registry 第二版切 LangGraph
追求”完全自主 Agent” 业务约束无体感、无审计、不可解释 退到 Workflow + HITL 中间态
追求”统一引擎” 不同场景特性差异大 按场景选（LangGraph/Hermes/Spring AI）

六、结论

先问场景，再问引擎。用得物的”有限状态机法则”判断：

  • 能画成状态机 + 需要 HITL → LangGraph
  • 需要快速可视化验证 → Dify
  • 需要 Skill 自学习 → Hermes
  • 需要省事 ReAct → Spring AI

对你的项目（可控 AI 工作流），推荐 Dify 起步验证 + LangGraph 生产落地，这是得物验证过的最低风险路径。

七、2026 主线演进：从”工作流引擎”到”AICoding 范式”（gap 深挖补充，2026-06-29）

上文一~六聚焦工作流编排引擎（LangGraph/Dify/Hermes/Spring AI），对应得物活动搭建/数仓/告警等场景。但 2026 年得物 AI 的真正主线已转向 AICoding，且补齐了基础设施层——这是另一条与”工作流引擎”并列的选型维度，不可只看引擎横评。

得物 2026 年 5-6 月密集发布 4 篇 AICoding 文章，构成 Spec 驱动三件套（统一内核=规格锁定意图 → 代理受控执行+验证 → 归档沉淀组织资产）：

7.2 基础设施层：大模型网关（id=204）

无论工作流引擎还是 AICoding，都需要模型供给底座。得物自研大模型网关”六步法”：模型市场 → 统一入口 → 全流程成本管控 → 稳定性架构 → 分钟级观测 → Key 生命周期管理。核心设计是调度器（选哪个模型）与路由模块（怎么转发）解耦——铁律”确定性机制锁定”在基础设施层的精确表述。收益：模型接入效率 +97%、单季 Token 成本 -45%、140 个模型 100% 纳管。

与 id=213 模型插拔的分层呼应：应用层插拔（id=213）vs 网关层统一管控（id=204），互补不重复。
