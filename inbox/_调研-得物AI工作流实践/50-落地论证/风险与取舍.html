风险与取舍

风险与取舍

汇总得物（活动搭建/数仓/告警）+ 高德（配图）实践中真实踩过的坑，及通用落地风险。

一、范式层风险（最致命）

风险 表现 对策
范式未变 AI 只是”帮你填字段”，价值不跃迁 灵魂拷问：AI 是辅助工具，还是流程主体？
追求完全自主 Agent 业务约束无体感、无审计、不可解释 退到 Workflow + HITL 中间态（得物选择）
黑盒化 无中间反馈、假进度条 每步解释”为什么、做了什么、缺什么”

二、架构层风险

风险 表现 对策（得物实证）
组件硬编码 加组件改中心调度，5 个还行 16 个崩 组件模块协议 + 开闭原则
副作用时机错误 用户看一眼卡片就产生脏数据 初始化只读，确认后才写（Phase 4）
多引擎维护成本 LangGraph+Hermes+SpringAI 并存 按场景选但要克制，记录选型理由

三、工程层风险（来自高德 + 得物告警的硬核实践）

风险 对策
LLM 数理计算不可靠（加权求和会算错） 模型只出原始分，总分由代码计算
结构化输出逃逸（返回非法枚举） 运行时白名单校验 + 重试
集中重试故障放大（VLM 抖动后批量重试压垮服务） 指数退避 + 随机等待
多机部署会话不一致 一致性哈希 + 分布式 DB
上下文膨胀（日志/数据量大） 工具返回分析摘要而非原始数据；指纹+知识匹配走快速通道
“LLM 验 LLM”循环（验收用 LLM 陷入循环） 格式用代码校验、内容才用 LLM；独立验收 Agent

四、LangGraph 特定风险

风险 对策
学习成本（图思维 vs 线性） Phase 1 先搭最小图，别一上来搞复杂
checkpointer 选型 开发用 InMemorySaver，生产必上 PostgreSQL/Redis
状态设计复杂（State schema） 从最小 TypedDict 起步，按需扩展
调试难（图执行路径多） 必接 LangSmith tracing

五、关键取舍清单（Taste Decisions）

取舍 推荐 理由
Workflow vs Agent 大框架 Workflow + 局部 Agent 可控性优先
可视化 vs 代码编排 Dify 验证 → LangGraph 生产 各取所长
单 Agent vs 多 Agent 单 Agent + 多能力模块（得物数仓） 保持上下文一致
自主 vs 人机协作 关键节点 HITL 信任建立 + 风险控制
重造 vs 复用 复用旧生态（得物 Form Host） 精力放在新增价值

六、一句话风险观

Agent/VLM 进入生产后，真正的挑战不是”跑通 demo”，而是在高并发、高成本、高风险下持续稳定跑。把”模型不可靠”作为第一假设，用代码/系统机制兜住所有不可靠的环节——这是得物+高德+本系列四篇文章共同的风险哲学。
