实现路径：从 0 到 1 落地可控 AI 工作流

实现路径

基于得物三版演进 + LangGraph 机制，给出从 0 到 1 落地一套可控 AI 工作流的分阶段路径。每阶段有目标、做法、代码骨架、完成标准。

总览

    P0["Phase 0<br/>Dify 验证范式"] --> P1["Phase 1<br/>LangGraph 最小图"]
    P1 --> P2["Phase 2<br/>Checkpointer 持久化"]
    P2 --> P3["Phase 3<br/>组件模块化"]
    P3 --> P4["Phase 4<br/>权限分级+副作用控制"]
    P4 --> P5["Phase 5<br/>监控+迭代"]

Phase 0：用 Dify 验证范式（1-2 周）

  • 目标：验证”AI 能否完成核心任务”，不追求生产级
  • 做法：Dify 可视化搭 2-3 个节点（解析 → 匹配 → 输出），验证 AI 的核心能力边界
  • 完成标准：核心任务能跑通，人工可以用起来
  • 得物对应：第一版（2 个 Dify Workflow 解析策划文档 + 语义匹配下拉选项）
  • 退出信号：发现”范式没变、组件硬编码、无持久化”→ 进入 Phase 1

Phase 1：LangGraph 最小可控工作流（1 周）

  • 目标：把验证过的流程用 LangGraph 重写为状态图 + interrupt
  • 代码骨架：
  • 完成标准：能跑、能 interrupt、能 Command(resume) 恢复
  • 关键纪律：LLM 只在 parse_node 做语义；路由/写操作在代码里（铁律）

Phase 2：Checkpointer 持久化

  • 目标：关掉浏览器再打开能继续（得物第二版核心特性）
  • 做法：InMemorySaver → 持久化 checkpointer（PostgreSQL/Redis）+ 稳定 thread_id
  • 完成标准：进程重启后，用同一 thread_id 能恢复到中断点

Phase 3：组件模块化（Capability Registry 思想）

  • 目标：新增场景不改核心调度
  • 做法：借鉴得物组件模块协议——
    • 统一生命周期（初始化 → … → 构建前 → 构建）
    • 双轨注册（显式选择 + 条件注入）
    • 开闭原则（对扩展开放，对修改关闭）
  • 完成标准：加一个新场景，只需注册新模块，不动核心图

Phase 4：权限分级 + 副作用控制

  • 目标：不产生脏数据（得物踩过的真实 bug）
  • 做法：
    • 三级权限：读（AI 可独立）/ 写（受控阶段）/ 发布（必须人工确认）
    • 副作用延后原则：初始化阶段绝不产生写操作，只有用户明确确认后才写
  • 完成标准：用户只”看一眼卡片”不会产生任何持久化数据

Phase 5：监控 + 迭代

  • 目标：可观测、可优化
  • 做法：
    • tracing（LangSmith）做全程可观测
    • 看板跟踪每步输入/输出/失败路径（参考高德六段式漏斗监控）
    • 灰度发布 + 回滚（参考得物”结果必须可回滚”）
  • 完成标准：每次执行可追踪，问题可定位

关键决策点速查

阶段 最易踩的坑 对策
Phase 0 沉迷 Dify 做生产 记住它只是验证工具
Phase 1 LLM 参与路由 路由握在代码里
Phase 2 thread_id 不稳定 用用户会话级 id
Phase 3 过早抽象 先有 3+ 同类再聚合
Phase 4 初始化偷偷写 副作用全部延后到确认后
Phase 5 只看成功率 看完整漏斗 + 失败路径
