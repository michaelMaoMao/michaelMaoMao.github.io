二、🔥 核心洞察：得物按场景选型（非统一引擎）

这是本调研最重要的发现——得物没有统一的工作流引擎，而是按场景特性选型：

场景 选型 选型理由
活动搭建（需可控状态机+人机中断） LangGraph interrupt/resume、checkpoint、HITL
数仓工作流（需自学习 Skill 资产化） Nous Hermes Skills 自主创建自优化（Learning Loop）
告警排查（需省事快速搭建） Spring AI ReactAgent 框架内置 ReAct 循环+工具拦截器，”省事”
第一版活动（解析策划文档） Dify Workflow 低代码可视化，快速验证

对用户原始需求的修正：用户问”得物用 langgraph + dify”——这仅是活动搭建一个场景的两版演进。得物完整生态是”多引擎按场景选型”。

推测性技术脉络（仅供后续深挖时参照，非实证）

基于提纲关键词，后续若拿到实质内容，可重点关注以下工程问题（均为客服 Agent 落地的公认难点，且与提纲一一对应）：

  • PE 自动化：可能是自动 Prompt 优化（如 DSPy/APE 类）、或基于 Badcase 回归的 Prompt 版本管理
  • RL 决策训练：Reward 设计是关键——是人工标注偏好（RLHF）、还是基于业务指标（解决率/CSAT）的 RLVR？提纲明确提到”设计 Reward 模型 + 采集训练数据 + 内化至 LLM 底座”
  • 经验蒸馏：用 Top5 人类客服的对话轨迹作为教师信号，蒸馏到 LLM（对应”对标 Top5”的预告）
  • 半双工对话：客服 IM 场景的经典问题——用户和机器人不能同时说话，需要消息发送时序控制（防止抢话、并发、意图切换时的中断处理）
  • 多轮协商：”既不得罪用户、又不违反平台规则”——典型的有约束生成（constrained generation）+ 规则护栏
