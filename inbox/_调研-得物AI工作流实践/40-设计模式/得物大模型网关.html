得物大模型网关：大模型时代的智能交通枢纽

自研大模型网关，以”六步法”（模型市场 / 统一入口 / 成本管控 / 稳定性架构 / 分钟级观测 / Key 生命周期）构建统一管控体系。网关 = 模型供给基础设施层：把”分散混乱、高门槛”的多模型对接，重构为”集中、透明、可量化评估”的标准化路径。得物版”确定性机制锁定（调度/限流/容灾）+ 模型只做语义感知（业务侧无感）”在基础设施层的精确表述。

量化收益：模型接入效率 +97%（单模型上架 1~2 天 → 10 分钟内；试用评估 1 天 → 5 分钟）；Q3/Q4 在用量环比翻倍情况下，每百万 Token 成本分别降 51.52% / 48.37%，半年降本达数百万元；内外部模型 100% 纳管（140 个模型）。

一、核心问题与动机：AI 流量指数增长 + 多模型管理挑战

得物 AI 应用从智能客服到代码生成、从金融法律分析到内容生成，深度融入核心业务。这带来四大挑战，也是自建网关的缘由：

  1. 资源浪费与效率瓶颈：需同时使用开源 / 商用 / 自建多类模型，API、数据格式、调用方式各异。每个业务域单建 → 技术栈碎片化、重复开发、”烟囱”林立；每个开发者直连 → 必须学每个 AI API、写供应商特定代码，效率低下。
  2. 成本失控风险：12 月 Token 消耗达数千亿规模，是 1 月用量的 20.63 倍，单月 Token 调用成本已是巨额。若业务各自对接公有云 → 使用与成本双双失控。
  3. 数据安全合规：敏感信息传外部 LLM → PIPL / GDPR 合规与数据泄露担忧。需自建以掌管数据主权。
  4. 稳定性保障：模型服务低限流阈值、延迟与成功率波动远大于传统 API；基于 Key 的固定限流易致业务间流量互相挤占；需实时告警 + 可观测性 + 完整请求日志（含 Prompt 与来源 IP）；需基于 Token（非调用次数）的精准配额从根源防滥用。

二、大模型网关定位：AI 流量的智能调度中心

与传统 API 网关的本质区别——传统网关面向 RESTful + 静态请求响应；大模型网关专门应对 AI 工作负载特有模式：

  • 长时与流式响应
  • 复杂输入输出
  • 高资源消耗与批处理
  • 上下文与状态管理
  • 专属监控与计量
  • 关注成本与业务效果（而非单纯 QPS/RT）

核心能力六维度：模型市场、模型体验、模型调度、模型成本、稳定性（可观测性 / 容量管理 / 模型流控 / 服务告警）。其中稳定性是”压舱石”——高可用、可管理、可追溯。

三、”六步法”详解（本文核心）

得物针对自身业务制定的六个落地策略，每一步对应一个核心痛点。

Step 1：打造信息丰富的模型市场（解决”选型门槛高”）

  • 本质：”AI 模型应用商店”——把分散混乱、高门槛的选型，重构为集中、透明、可量化评估的标准化路径。
  • 四大闭环能力：
    • 模型纳管：集中管理自研 + 内外部厂商模型，形成内部”模型货架”，消除信息碎片；原生支持托管与上云对接。
    • 评测对比：支持文本生成、图像理解/生成等对比测试，真实业务问题一键投递多模型直观比拼。
    • 一站式接入：选定模型即查 API 接入指南，完成”选型-试用-接入”闭环。
    • 运营与推荐：按效果与性价比打标、置顶，缩短选型时间并助力降本。
  • 效果：模型上架 1~2 天 → 10 分钟内；试用 1 天 → 5 分钟以内。

Step 2：统一各业务模型服务入口（解决”烟囱与重复开发”）

  • OpenAI-like 风格统一访问 API + 模型服务调度：绝大部分 AI 服务访问集中到单一入口。
  • 业务线无需关注后端模型实现细节，并天然实现不同厂商模型服务间的容灾。
  • 这是”厂商无感接入体验”的根基——统一分发 API Key + 统一 API，业务无需关心各厂商入参/出参差异。

Step 3：建设全流程成本管控体系（解决”成本失控”）

围绕 “源头管控、成本感知、模型调度、厂商折扣、成本监控” 五方面搭闭环，打通”预算申请 → 模型选型 → 接入调用 → 运行观测 → 成本结算”全链路。

正在建设的精细化降本能力（核心思路）：

  • 构建 Key / 模型 / 厂商 / 项目维度的成本大盘
  • 构建各外部厂商各类别模型均价大盘（发现更有性价比的模型）
  • 建设用量与成本每周主动推送机制
  • 完善成本预警 / 告警体系
  • 促使业务依据成本与价格数据主动进行成本治理（而非被动事后核算）

Step 4：持续夯实稳定性架构能力（解决”波动与挤占”）

围绕 “高可用、可控成本、稳定体验” 三目标，重点建 限流、调度、容灾 三类核心能力，实现分钟级容灾切换。

  • 容量管理与限流：模型容量配置化管理，按 Key / 项目维度做 TPM 容量管理；流量（token）超阈值即触发限流 + 容量告警。
  • 模型调度与容灾：厂商间模型粒度的分钟级容灾。机制——若检测到当前 API Key 配置有调度策略，模型调度器按规则执行调度，选中模型交付给模型路由模块，路由模块封装后转发到对应厂商服务。

关键架构拆分：调度器（选哪个模型） 与 路由模块（怎么转发） 解耦——这正是”确定性机制锁定”的体现，策略可配、执行可审计。

Step 5：建设分钟级实时观测能力（解决”黑盒运行”）

原文金句：”没有分钟级观测体系的模型网关，就像没有仪表盘和刹车的 F1 赛车——速度越快，风险越大，毁灭性越强。”

  • 调用/用量/性能观测：已实现 Key 与模型粒度的调用次数、Token 用量、失败率、平均 RT、RPM/TPM 监控大盘。
  • 模型成本观测：模型 / Key / 厂商 / 项目粒度实时大盘 + 日/周/月/指定时间汇总。
  • 模型异常告警：基于 Flink 实时计算 + Kafka 事件订阅，建设模型与 Key 粒度实时告警体系，目标3 分钟内飞书告警触达。

Step 6：建设 Key 生命周期管理能力（解决”配额与鉴权散乱”）

API Key 管理产品化：

  • 申请工单 + 自动分发
  • 场景 / 负责人 / 共享人 / 状态管理 + 黑名单
  • 依托 Key 实现接口鉴权、预算管理（分配/消耗/预警）、容量管理、模型调度等核心功能与关键流程节点的规范化管理。

Key 是网关的”原子控制单元”——预算、容量、调度、鉴权全部以 Key 为锚点串起来。

五、网关如何保障成本/安全/稳定性（具体机制汇总）

成本

  • 预算闭环：预算申请（Key 工单）→ 调用监控 → 预算预警 → 模型调度（切高性价比模型）→ 费用查看
  • Token 级配额（非调用次数），从根源防滥用
  • 智能调度降本：请求优先分配至性价比更高的模型——既是容灾手段，也是降本利器
  • 均价大盘 + 每周推送：让业务主动发现更优模型

安全

  • 自建掌管数据主权：敏感数据不出私域，规避 PIPL/GDPR 风险
  • Key 鉴权 + 黑名单：接口鉴权规范化
  • 完整请求日志：含 Prompt 与来源 IP，便于追踪审计

稳定性

  • 容量管理：按 Key/项目 TPM 配置化，预估业务流量预配额度
  • 限流：Key 与模型粒度的 TPM/QPS 流控，超阈值依规则限流
  • 模型调度与容灾：调度器 + 路由模块解耦，厂商间分钟级切换
  • 实时观测：调用/用量/性能/成本多维大盘
  • 实时告警：Flink + Kafka，3 分钟内飞书触达

六、创新亮点（核心技术突破）

  1. 全流程成本管控体系：预算-Key-调用-监控-预警-调度-结算闭环
  2. 跨厂商模型级容灾：显式或默认调度策略，优先分配高性价比模型（容灾 + 降本双效）
  3. 厂商无感接入：统一 API Key 分发 + 统一 API，屏蔽入参/出参差异
  4. 便捷高效模型选型：模型市场 + 试用预算池 + 效果对比 + 推荐
  5. 分钟级用量与成本观测：调用量/失败率/RT/TPM/RPM 实时监控，成本按周推送

七、可借鉴点 与 主线的关系

网关 = Claude Code/SDD/MCP 体系的”模型供给底座”

得物 AI 主线（Claude Code + SDD/Spec + MCP）的模型供给基础设施就是这座网关。它和 id=213 的”模型插拔”形成分层呼应：

层次 机制 关注点
应用层（id=213 Claude Code 工作流） 模型插拔（多 Agent 主从 + 模型按角色选型） 单个 Agent 任务用什么模型最优
网关层（id=204 本篇） 统一管控（调度/限流/容灾/成本/Key） 全组织模型流量如何高效、安全、经济地供给

两者互补不重复：应用层插拔解决”任务-模型匹配”，网关层管控解决”供给-成本-稳定”。应用层的每一次模型调用，最终都流经网关被调度、计量、容灾。

与铁律的精确对应

网关层把”确定性机制锁定“具象为：调度器+路由模块解耦、Key 粒度配额、Flink 实时告警、分钟级容灾——这些全是确定性代码/配置掌控，模型只负责业务侧语义感知（且对业务无感）。

可迁移要点

  1. 统一入口 + OpenAI-like API：屏蔽厂商差异，业务无感，天然容灾——任何多模型组织都该优先建
  2. Key 作为原子控制单元：鉴权/预算/容量/调度全部以 Key 串起来，简化治理
  3. Token 级而非调用次数级配额：从根源防滥用，匹配大模型真实资源消耗
  4. 模型市场 + 试用预算池：把选型从”1~2 天调研”压缩到”5 分钟对比”，大幅降低 AI 接入门槛
  5. 调度即降本：请求优先路由到高性价比模型，容灾与降本同一机制
  6. 分钟级观测是前提：没有实时观测的网关 = 没有仪表盘的赛车，规模化前必须先建

八、未来演进方向

  1. 持续成本管控主体责任：强化数据分析推进精细化降本；落地 Qwen 系列自建模型通过云商托管方式降本
  2. 标准化与生态兼容：引入并适配 MCP（模型上下文协议）；API 同时兼容多厂商 + 多形态模型（文本/图像/语音/视频/多模态），一致体验下跨生态无缝互通
  3. 从流量管理 → AI 编排平台：在模型调度基础上建更强工作流与多模型协同机制，按成本/延迟/准确性将请求分配给最优模型
  4. 终极定位：从”网关”演进为企业智能化的”神经中枢“——不直接思考，但确保思考过程高效、安全、经济地发生

九、局限 / 待验证

  • 具体调度算法未披露：调度器”按配置规则执行调度”，但规则是加权/轮询/最低延迟/最低成本？未细化（推测含性价比优先 + 容灾 fallback）
  • 成本降低的归因拆分不足：51.52% / 48.37% 的降本中，多少来自调度切换、多少来自厂商折扣谈判、多少来自业务侧 prompt 优化？未拆分
  • 自建 vs 商用网关的选型论证缺失：行业实践图表提及多家商用方案，但得物为何选自建（而非用 Higress/Kong AI 等）未深入论证
  • 数据安全机制细节有限：仅提及”自建掌管数据主权” + Key 鉴权 + 日志审计，未见脱敏/加密/DPF 等具体技术栈
  • MCP 适配尚在规划：未来方向提到”引入适配 MCP”，当前网关与 MCP 的具体集成方式（是否作为 MCP Server 暴露模型能力）未明确
  • 观测大盘截图为主，告警规则阈值未给出：实际限流/告警的数值配置需进一步了解

调研库关联：本篇与 id=213（Claude Code 工作流·模型插拔）构成”应用层插拔 vs 网关层统一管控”的分层呼应；与 id=217（Galaxy MCP）共同指向 MCP 协议在得物 AI 基础设施中的逐步渗透；”调度器/路由模块解耦”是铁律”确定性机制锁定”在基础设施层的精确表述。
