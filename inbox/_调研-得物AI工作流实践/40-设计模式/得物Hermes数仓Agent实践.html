从埋点需求到规则资产：Hermes Agent 重构得物数仓工作流

本文系腾讯云开发者社区转载得物技术团队原创文章，发布于 2026-06-18。原始出处可追溯至微信公众号”得物技术”。多平台同步转载：知乎专栏、InfoQ、CSDN、掘金、开源中国、tool.lu 等。
调研备注：腾讯云页面正文为前端动态渲染，反爬严格；本文内容综合多平台公开摘要、目录信息与相关延伸文章重建，非逐字原文，侧重提炼技术骨架与设计模式。如需原文措辞请直接访问 source 链接。

一、问题背景：数据承接方真正消耗精力的是什么

文章开篇点题的核心论断：

在埋点和指标需求里，最消耗数据承接方的不是”生成答案”，而是——补齐证据链、对齐历史口径、识别下游影响，并在生产写入前留下可追溯的确认记录。

文中术语约定：

  • 数据承接方：承接业务需求的数据同学或业务合作伙伴。
  • 流程中还涉及”内部研发、元数据、查询和门禁”等能力的角色定位。

具体的旧流程痛点（分散信息需要重新拼起来）：

  1. 动作采集必要性判断：需求文档里的某个动作到底要不要采集？
  2. 历史点位比对：历史上有没有类似点位，是否重复或冲突？
  3. 指标口径核查：指标口径有没有被下游引用，是否需要对齐既有定义？
  4. 下游影响识别：变更或新增埋点对下游数据消费方的影响范围。
  5. 可追溯性缺失：生产环境写入前缺乏留痕，出了问题难以回溯。

这些工作本质是工程化的证据收集与风险预演，而非创造性判断。这正是 AI Agent 能够切入的空间：让 AI 负责工程化准备，让人专注于业务决策。

二、框架选型：为什么选 Hermes Agent 而不是 OpenClaw

2.1 候选与对比

得物团队在选型时对比了两类开源 Agent 框架：

维度 Hermes Agent（选用） OpenClaw（未选）
维护状态 活跃维护 已停止开发
持续在线 支持 较弱
持久记忆 分层持久记忆 依赖外部存储
技能沉淀 Agent 自主创建、自优化的 Procedural Memory 静态文件，人工编写
多平台接入 Gateway 层统一适配 插件化
架构理念 “轻量后端 + 重 Agent 循环” “重 Gateway 平台 + 分布式 Node 架构”

2.2 选型结论

文章明确指出：

Hermes Agent 因其持续在线、持久记忆和技能沉淀能力，优于 OpenClaw，尤其适合处理埋点和指标需求这类长流程、需经验沉淀的场景。

关键澄清见本文「调研笔记」一节。

三、架构核心：单 Agent 编排 + 多能力模块 + 看板确认点

3.1 为什么不做多 Agent

得物没有把能力拆成”一组互相独立的智能体”，而是采用：

“单 Agent 编排 + 多能力模块 + 看板确认点”

理由：

  • Hermes Agent 保持统一上下文，负责调度阶段流转；
  • 能力模块承接稳定、可复用的工程化逻辑；
  • 多 Agent 会割裂上下文，而埋点流程强依赖跨阶段的上下文一致性（前一阶段的证据要被后一阶段引用）。

3.2 四个可追踪的工程构件

在这套框架之上，得物把”一次埋点需求承接”拆解为四个可追踪的工程构件：

1. 工作区（Workspace）

  • 每个需求一个独立空间；
  • 集中存放：需求文档、历史讨论、评审结论、交付产物；
  • 作用：让上下文固化、可检索、可回放。

2. 看板（Kanban）

  • 状态流转可视化；
  • 跟踪需求从提出到交付的全生命周期；
  • 关键角色：人工确认点——AI 完成工程化准备后，在看板上停下等人工决策拍板，而非自动放行。

3. 规则（Rules）

  • 将埋点规范、承接经验沉淀为可复用的规则资产；
  • 后文第四节专门展开。

4. 工具接口（Tool Interface）

  • 把查询、绑定、发布、验证这些动作，包装成参数明确、返回结构化、过程可审计的接口；
  • 核心原则：

    越靠近写入，越要先预演、再确认、最后留痕。

四、总体工作流：从一次对话变成一条可回放链路

4.1 工作流主线（四件事）

Hermes Agent 在埋点需求链路上的核心价值是可回放、可确认、可复用的工作流能力。当前链路围绕四件事形成主线：

  1. 跑通需求流转——让需求在各阶段间可控地流转，而非散落在聊天记录里；
  2. 前置风险拦截——在写入生产前预演变更、暴露冲突；
  3. 沉淀规则资产——把每次承接的经验固化为可复用规则；
  4. 让数据承接方把精力放在判断上——AI 做工程化准备，人做业务决策。

4.2 五个可复用的流程模块

这些能力模块不是只服务一次埋点需求，而是被抽象成可复用的流程模块：

模块 职责
素材采集 收集埋点需求所需的上下文与事实源（需求文档、历史点位、指标口径）
历史检索 基于分层记忆系统检索历史埋点/指标规则与变更记录
变更预演 发布前对规则变更做风险预演，固化事实、提前暴露风险（如重复点位、口径冲突）
发布确认 人在回路（Human-in-the-loop）做最终决策确认
经验沉淀 将每次需求过程中的经验转化为可复用的技能与规则资产

文中强调：换事实源和工具接口后，同一套机制也可复用到其他类似流程（指标需求等）。

4.3 流程特性

  • 事实源（Source of Truth）聚焦：把分散信息重新拼合并固化为”事实”，作为后续处理的可信基础；
  • 预演验证：在正式执行前进行风险预演；
  • 人工确认：通过看板设置确认节点，形成 Human-in-the-loop 闭环；
  • 审计留痕：每一步动作过程可审计，支持事后回放。

五、能力底座：把规则、上下文和命令资产化

5.1 什么值得沉淀

第四节聚焦”什么值得沉淀“。文中指出：

埋点自动化真正难的是，把历史口径、下游影响、人工确认和生产状态拆成可复用资产。

三类被资产化的对象：

  • 规则（Rules）
  • 上下文（Context）
  • 命令（Commands）

5.2 资产化的工程意义

  • 可验证执行：规则资产化后，执行过程可被验证、可被回归；
  • 协作可见性：团队协作中，规则是显式共享的，而非隐式知识；
  • 结构化工具接口：工具接口沉淀为资产后，新流程可直接复用；
  • 风险治理：资产化的规则让人工确认点、审计留痕有据可依。

六、量化效果

重要说明：综合所有公开转载版本与搜索摘要，本文未检索到明确的量化数据指标（如效率提升百分比、人力节省、缺陷率下降等）。文章以方法论与架构设计为主，效果部分多为定性描述（”让数据承接方把精力放在判断上”、”流程可控”等）。如需量化数据，建议查阅得物技术后续文章或相关分享。

七、可借鉴的设计模式

从本文可提炼出几条对通用 Agent 工程有参考价值的设计模式：

模式 1：单 Agent 编排 + 能力模块化（避免多 Agent 上下文割裂）

适用于强依赖跨阶段上下文一致性的长流程。多 Agent 各自维护上下文会导致证据链断裂；单 Agent 统一调度 + 能力模块承接稳定逻辑，兼顾上下文一致性与工程化复用。

模式 2：四构件骨架（工作区 / 看板 / 规则 / 工具接口）

将一次性任务拆解为四个可追踪的工程构件，让流程从”散落在对话里”变为”可回放的链路”。这套骨架与具体业务解耦，可复用到指标需求、配置变更等场景。

模式 3：越靠近写入，越要”预演-确认-留痕”

工具接口设计的核心原则。把查询/绑定/发布/验证包装成参数明确、返回结构化、过程可审计的接口，并在越靠近生产写入的节点设置越严格的人工确认。

模式 4：Human-in-the-loop 的看板化

人工确认点不是简单的 yes/no 弹窗，而是看板上的可视化节点。AI 做完工程化准备后”停下”，把决策权显式交还给人。

模式 5：经验沉淀为规则资产（Skills 自进化）

把每次承接过程中稳定下来的经验固化为规则/上下文/命令资产，让 Agent 在下次同类需求中直接复用，形成自进化闭环。

模式 6：Workflow 优于一次性 Agent 对话

文章隐含的选型倾向：对于有固定阶段、需要审计留痕、需要经验沉淀的工程化场景，应构建可回放的工作流链路，而非一次性 Agent 对话。

关于”得物 Hermes 是什么”的关键澄清

这是本次调研最重要的澄清点，与任务简报中的假设存在出入：

  1. Hermes Agent 不是得物自研。它是 Nous Research 开源的通用 AI Agent 框架，定位为”The agent that grows with you”——自改进 Agent，内置学习循环（Learning Loop），能从经验中自主创建 Skills。
  2. Hermes Agent 不基于 LangGraph。它基于 Python 构建，核心是自研的”轻量后端 + 重 Agent 循环”架构，与 LangGraph 无直接关系。
  3. 得物的角色是”应用方”：得物技术团队选用开源的 Hermes Agent 作为底座，在其上构建了”单 Agent 编排 + 四构件 + 能力模块化”的数仓工作流方案。文中对比的 OpenClaw 是同类竞品（另一个开源 Agent 平台），二者常被并列讨论。
  4. 架构关键词：Gateway（多平台接入层）、Memory（分层持久记忆）、Skills（Procedural Memory，Agent 自主创建自优化）、Scheduler。Hermes 与 OpenClaw 的核心架构分歧在于 Skills 的产生方式——Hermes 是 Agent 自进化，OpenClaw 是人工编写静态文件。

文章质量评价

  • 优点：方法论清晰，”单 Agent + 能力模块 + 看板确认点”的架构选型论证扎实；四构件骨架（工作区/看板/规则/工具接口）抽象到位，可迁移性强；”越靠近写入越要预演-确认-留痕”是很好的工具接口设计原则。
  • 不足：缺乏量化数据是硬伤，通篇定性描述；架构图只能从文字描述推断；对 Hermes Agent 框架本身的能力（Learning Loop 具体如何运作、Skills 如何自进化）着墨不多，更多是应用层设计。
  • 适用读者：正在为企业内部长流程（非仅数仓）选型 Agent 架构、纠结单 Agent vs 多 Agent、或需要设计”可审计工作流”的工程师与架构师。
