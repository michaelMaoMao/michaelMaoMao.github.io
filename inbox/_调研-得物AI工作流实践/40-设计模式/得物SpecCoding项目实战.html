得物 AI 编程能力边界探索：基于 Claude Code 的 Spec Coding 项目实战（id=212）

得物 Spec Coding 项目实战：用三层规范消除 AI 不确定性

一个工程师 + Claude Code，10 天从 0 到 1 搭建企业级中后台，2.5 万行净增代码、2,754 次工具调用、提效 36%。本文是 Spec 驱动三件套的项目实战层——把 id=216 的工程化理论与 id=213 的 SDD 工程落地，落到一个真实可量化的项目上,并给出 AI 编程的能力边界框架与三种失效模式。

元信息与一句话定位

  • 项目：企业级知识问答平台（中后台搭建），涵盖表格、表单、卡片列表、数据看板等核心场景，从零搭建全程 Claude Code 辅助。
  • 核心命题：AI Coding 的本质不是”让 AI 写代码”，而是用结构化的规范和工作流把不确定性消除在执行之前——AI 在确定性空间高速执行,人维护那个确定性空间的边界。
  • 一句话总结（原文）：规范是杠杆，AI 是力，Spec 工作流是支点。
  • 在本系列的位置：Spec 驱动三件套的项目实战层——id=216=理论总论（为什么工程化），id=213=工程落地（怎么干），本文=干成什么样（量化收益 + 能力边界 + 失效模式）。

一、核心问题与动机：为什么用 Spec Coding

1.1 重新理解”AI 辅助编程”是什么

作者反对流行的”AI 是你的 Copilot”比喻，提出更精确的模型：

AI 是一个极度服从、无限耐心、但没有内部业务知识常识的”顶级执行者”。

三个关键特征：

特征 含义 双刃剑
极度服从 一字不差地执行规范，不会主动质疑”这样合理吗” 规范越准确越可靠；规范有歧义，AI 会选”看起来合理”的解释而不是停下来问
无限耐心 34 个任务重构、9 组联调、跨会话恢复——AI 无摩擦成本 208 次 TodoWrite 调用背后是 AI 持续更新进度、从不嫌烦
没有内部业务常识 不知道部署环境、不知道接口上周刚换版本、不知道交互做成这样用户会抱怨 这是构建排障花费大量时间的根本原因

1.2 为什么需要 Spec Coding

Spec Coding（规格驱动编码）核心思想：在写代码之前，先写规格文档。通过 openspec 工具，每个功能变更经历 proposal → design → specs → tasks 四阶段。

三个实际价值：

  1. 减少返工：proposal 阶段明确为什么/怎么做，避免实现完才发现方向不对
  2. 适合复杂功能：对跨多文件多层级的功能，tasks 分组让 AI 聚焦当前步骤
  3. 可审计：每个 Change 的完整决策链都留有记录，方便回溯

三、关键设计：三层规范体系（约束 + 示范 + 视觉）

3.1 三层结构的设计思想

本项目规范体系是三个层次的协同约束，每层解决不同的问题：

为什么需要三层：只有”约束层”时，AI 知道规则但缺乏参考实现，容易在复杂场景下产生符合规则但不符合团队风格的代码。加入”示范层”和”视觉层”后，AI 可以直接对齐团队的标准产出，减少”虽然合法但不地道”的代码。

3.2 第一层：约束层（.claude/rules/）—— 7 个规范文件

3.3 第二层：示范层（.claude/code-design/）—— 标准模板代码

预置项目常见场景的完整标准模板，AI 生成新页面时可直接参照（后续可切换为 skills）：

示范代码不只是”看个格式”。例：开发者说”参考 .claude/code-design/pro-table 生成知识治理列表页”，AI 直接继承这套模式，一次就能生成符合团队风格的代码，无需多轮调整。

实践结论：提供 HTML 设计稿后，AI 生成的 UI 与设计意图的吻合度明显高于纯文字描述，尤其是布局结构、颜色方案、间距配置等细节。

3.5 三层规范的实际效果

正面效果（规范被遵循的案例）：

  • 接口命名一致性：所有接口函数均以 fetch{Name}Api 命名，类型以 I{Name}Req/Res 格式，205 个文件保持高度一致
  • 目录分层被遵守：constants/、services/、hooks/、components/ 分层在每个新页面中都被正确创建
  • 代码模板被继承：CRUD 页面均参照了 pro-table 模板的 hooks 分离方式
  • 使用可选链：几乎所有数据访问都使用了 ?. 和 ??，有效避免运行时报错

需要人工干预的案例：

  • 2/24，AI 将知识空间列表所有代码写在单文件中，未按规范分层 → 一条追问后重构为正确结构
  • 2/27，AI 错误地使用了 .less 后缀（项目实际配置 SCSS） → 收到错误提示后立即修正
  • 出现 antd v5 废弃 API（destroyOnClose、dropdownStyle），AI 习惯使用训练数据中更常见的旧 API → 需通过报警信息触发修正

核心结论：规范体系对 AI 的约束是有效的，但规范文件只是”约束”而非”能力”——只有约束层时，AI 知道不能做什么但复杂场景仍可能不够地道；加入示范层和视觉层后，AI 有了对齐锚点，输出质量和一致性明显提升。

四、典型案例（四个，覆盖 AI 全部能力面）

4.1 案例一：AI 驱动产品设计（一人分饰三角）

背景：传统 0→1 企业级知识问答平台需要 PM（需求+PRD）+ UI 设计师（交互+高保真稿）+ 工程师（编码）三个角色。本案例让 AI 在不同阶段扮演不同角色，一个工程师覆盖全部职责。

阶段 AI 扮演 实现机制
产品经理 「首席产品专家」Persona 提示词植入 Rules 把 AI 从工程师的”急于执行”模式切换为 PM 的”先想清楚”模式
UI 设计师 在 Rules 中定义设计规范 对话式生成逐页产出高保真 HTML 文件（不是源码）
文档生成 基于 PM 角色 将 HTML 设计稿作为上下文，生成精确到组件行为级别的 PRD

关键产出：一套可直接用于开发对齐的视觉参考 + 研发可读的 PRD，也是后续 AI 生成代码时的重要上下文来源。

4.2 案例二：SDD 驱动前端功能研发（SDD + MCP 联调提效）

场景：在已有系统上增量交付「定时任务管理」完整模块，对接 6 个后端接口。这是 SDD 工作流第一次被完整运用于新功能模块开发，也是验证「SDD + MCP」前后端联调提效的关键场景。

三个维度的执行结果：

维度 结果
页面功能开发 opsx:new 到 archive 全流程，人工指令 < 10 条，AI 代码占比 100%，交付完整任务管理模块（独立路由 + 完整 CRUD + 执行记录 + 检索结果）
前后端联调 SDD + MCP 路径：接口 URL → MCP 直连文档 → 一次性获取字段/枚举/必填项 → 接口文件一次生成 → 联调一次通过，6 个接口零联调返工
研发效率 同日额外交付两个完整模块，3 个独立完整模块单日全部开发完成，按纯人工开发当天人效提升 3 倍

4.3 案例三：SDD 驱动系统重构（在活体系统上动手术）

重构与新功能的根本差异：

  • 新功能开发是”从无到有”：AI 可以大胆生成，错了删掉重来。
  • 重构是”在活体系统上动手术”：高风险对 AI 提出截然不同的要求——不仅要知道改什么，更要知道不能改什么，以及按什么顺序改。

SDD 的价值正在于此：在动代码之前，把这三件事全部写清楚。

知识问答首页重构案例：

  • 架构债务：大量首页业务组件与公共组件混放、useChat 导出 20+ 方法（4 种无关职责混合）、ChatInterface 接收 17 个 props（参数 3 层传递）
  • 执行 TASKS：9 组 34 个子任务，从「grep 确认组件当前归属」→「按新分层迁移」→「更新所有 import 路径」→「tsc 类型检查」→「冒烟验证」，每一步有明确输入和验收标准
  • 执行结果：34 个任务全部完成（含 4 个验证任务），AI 全程独立执行，人工干预 < 5 条指令；7 个业务组件与公共组件完成解耦，useChat 拆为 3 个单职责 hook，ChatInterface 从 17 个 props 缩减至 6-8 个

4.4 案例四：复杂问题排障（AI 的能力边界）

场景：测试环境构建失败，过程约 4 小时、7 个会话、15+ 次方案尝试、59 条指令——整个项目单日指令最多的一天，也是 AI 独立解决能力最受限的一天。

关键特征：AI 每次分析都是正确的，但问题仍无法解决——问题不在 AI 分析能力，而在问题的结构性特征超出 AI 的信息范围：

结构性障碍 具体表现
云服务器构建时发生，本地无法复现 每次验证必须提交代码等待 CI（一轮约 10 分钟），AI 分析的是日志截图，无法感知”现在的 CI 环境还有哪些隐性配置”
多根因互相掩盖 解决一层才暴露下一层；AI 每次分析都正确，但只分析了当前暴露的那一层，问题全貌无法被单次分析覆盖
隐性行为无文档，根因藏在依赖源码内部 Prisma postinstall 境外下载没有任何显式错误，AI 不得不深入阅读 node_modules 源码第 2319 行才能发现根因

最终确认的三个根因：

  1. .npmrc 历史副作用：早期为跳过 @next/swc-darwin-arm64 在 Linux 下载而加入的 omit=optional，无意间也跳过了 @tailwindcss/oxide-linux-x64-gnu（Tailwind v4 的 native binding），postinstall 陷入循环等待
  2. Prisma v6 境外下载沉默卡死：AI 需阅读 node_modules/@prisma/fetch-engine/dist/index.js 第 2319 行才能发现——postinstall 不报错、不超时，只是无限等待
  3. pnpm 跨平台 lockfile 不一致：macOS arm64 生成的 lockfile 不含 Linux x64 的 native package；切回 npm 则 lockfile 被忽略，安装结果每次不同

最终解法（4 小时探索后）：

  • 锁定 tailwindcss@4.1.11，配置 PRISMA_ENGINES_MIRROR=https://registry.npmmirror.com/-/binary/prisma
  • 统一使用 pnpm，CI 命令同步更新，删除 .npmrc 中的 omit=optional

五、MCP 工具：消除信息断层

AI 辅助前端开发中，有两类高频信息断层：

5.1 MCP 一：接口文档直连

  • 断层：接口文档在 API 平台，AI 无法直接访问，只能靠用户手工复制字段，易遗漏、版本不一致
  • 能力：AI 根据接口 URL 自动拉取完整接口文档——入参字段、出参结构、枚举值、必填项；服务端接口未生效之前支持同步生成 mock 数据
  • 数据：累计被调用 21 次，完成 39 个接口联调，覆盖几乎所有接口的初次接入和更新迭代
  • 质量：interface.ts 类型定义质量非常高，字段注释完整，无需人工校对

5.2 MCP 二：飞书云文档直读

  • 断层：PRD、设计文档存在飞书云文档中，每次引用都需要用户打开→复制→粘贴到对话框，打断思路
  • 能力：AI 直接读取飞书云文档内容（PRD、设计说明、技术文档等），无需用户手工打开→复制→粘贴

与 id=217 Galaxy MCP 同源——都是用 MCP 消除”AI 看不到外部系统”的信息孤岛。

六、AI 编程的能力边界框架（核心洞察）

6.1 按需求颗粒度选择协作模式

真实项目中并不是所有需求都值得写一份 Spec。需根据需求颗粒度选择协作模式：

颗粒度 场景 策略 理由
小颗粒 改文案、修显隐、调 CSS 间距 对话框即扫即改（Cursor Chat） 沟通成本低于编写规范的成本，AI 即时反馈效率最高
中颗粒标准化 标准 CRUD 页面、简单业务组件 基于预设 Rules/Skills 生成（如 pro-table.mdc） 需求有强烈”模式感”，规则定义清晰 AI 即可基于模板高质量输出
中大颗粒复杂 重构核心逻辑、新增复杂业务逻辑模块、无参考代码的新功能 OpenSpec 标准流（SDD） 业务逻辑复杂时 AI 极易幻觉或需求偏移，Spec 强制”先设计后编码”保证每步在既定轨道上

6.2 AI 失效的三种模式（可归类，不是随机的）

失效模式 表现 发生频率 应对
模式一：规范真空 任务涉及领域没有规范约束，AI 自行填充”合理默认值”；代码功能正确但风格/结构偏离团队约定 高（尤其新功能开发初期） 在 CLAUDE.md 或 code-design 中补充对应规范，一次修复全局生效
模式二：信息孤岛 AI 掌握的信息是当前会话快照，看不到系统外状态；本地正常 CI 失败；AI 分析每次都对但解的都是当前暴露的问题 低，但代价高 跨平台/跨环境的依赖要在架构设计阶段提前锁定；环境差异要写成规范前置处理
模式三：任务目标模糊 AI 把”该问人的问题”当成”执行问题”来解决；用户说”优化一下首页”，AI 悄悄改了组件结构而不是先澄清目标 中 Spec 工作流的 proposal 阶段强制要求先描述「Why」，避免 AI 自行填充目标

七、开发者角色的重构

AI Coding 不是让开发者”消失”，而是让开发者的工作向上迁移：

新核心竞争力 含义
规范设计能力 能写出让 AI 可靠执行的规范，价值比能写出同等功能代码更高
系统性思维 生产构建排障经历说明，AI 可以帮你解决每个局部问题，但无法帮你看到真实业务全局
质量意识前移 过去 Code Review 在代码写完后进行，现在需要在方案设计/任务执行阶段就介入，而不是等 AI 执行完再纠错

八、可借鉴点

  1. 三层规范体系（约束+示范+视觉）是 CLAUDE.md/Rules 的进阶版——光有约束不够，必须给”标准产出长什么样”的锚点。可直接用于评估任何 AI Coding 规范体系的完备度。
  2. Spec 不是银弹，按颗粒度选择——小颗粒对话、中颗粒 Rules、中大颗粒 SDD。避免”所有需求都写 Spec”的过度工程化。
  3. AI 失效三模式可直接套用——规范真空/信息孤岛/目标模糊，是任何 AI Coding 实践都会遇到的三类失效，应对策略可复用。
  4. MCP 是消除信息孤岛的关键基础设施——接口文档、飞书文档直连，与 id=217 Galaxy MCP 同源，是”AI 看到外部系统”的统一机制。
  5. SDD + MCP 组合拳——案例二验证了”SDD 定义任务 + MCP 直连外部信息”的组合，可实现 6 个接口零联调返工。
  6. 重构 vs 新功能差异化策略——重构是”在活体系统上动手术”，SDD 的价值在于事先把”改什么/不改什么/按什么顺序改”三件事写清楚。
  7. 质量意识前移——Code Review 从代码后移到方案设计/任务执行阶段，这是 AI 时代工程师的新工作方式。

九、与已挖研究的关系（Spec 驱动三件套）

本文与 id=216 OpenSpec 理论总论、id=213 Claude Code 工作流工程落地，构成完整的 Spec 驱动知识三角：

文档 侧重 角色
id=216 理论总论 + 工具解构 为什么必须工程化（上下文工程 + SDD 范式论证 + DORA/GPT-4o 数据）
id=213 工程落地 怎么干（模型插拔 + 多 Agent 主从 + SDD 三阶段）
id=212（本文） 项目实战 干成什么样（量化收益 + 能力边界 + 失效模式）

三者的统一内核：

具体呼应点：

十、局限与待验证

  1. 单项目样本：所有数据来自一个 0→1 项目，增量改造/大型遗留系统的适用性未验证——案例三的重构虽有验证但只覆盖首页一个场景
  2. 提效 36% 口径未拆解：未说明对比基线（同等功能纯人工开发预估工时？历史同类项目？），36% 是整体还是某阶段，难以直接复用为预测模型
  3. 三层规范的维护成本未量化：7 个规范文件 + 6 类示范模板 + N 个 HTML 设计稿是手动维护的，长期演进成本（规范过期、模板失同步）未讨论
  4. “AI 代码占比 100%”需谨慎解读：占比按代码行计还是按决策权计？spec 是人写的，决策是人审的，AI 只做执行——严格说”100% AI 代码”是指”AI 敲键盘”而非”AI 决定做什么”
  5. 构建排障案例的普适性：4 小时排障解出的是具体的 Prisma/Tailwind v4/pnpm 组合问题，方法论（多根因互相掩盖/隐性行为无文档）可复用，但具体技术根因不具普适性
  6. MCP 工具的实现细节缺失：接口文档直连 MCP、飞书文档 MCP 的具体实现（是通用 MCP 还是自研）未说明，复用需自行实现
  7. 能力边界框架的颗粒度：三颗粒度（小/中/中大）+ 三失效模式（真空/孤岛/模糊）是经验归纳而非严格分类，边界存在灰色地带（如”中等颗粒但有复杂业务逻辑”该用 Rules 还是 SDD？）

十一、未来方向（原文展望）

  • 规范体系的结构化积累：建立”踩坑→提炼规范→自动追加”的闭环，目前 7 条规范手动维护
  • MCP 工具链的纵向延伸：从接口文档/飞书文档扩展到设计稿、测试用例、发布平台、日志平台，形成完整 AI Coding 链路
  • 多 Agent 并行开发：大型任务执行等待时间较长，可尝试多 Agent 并发，同时开发不同功能模块（呼应 id=213 的多 Agent 主从架构）
