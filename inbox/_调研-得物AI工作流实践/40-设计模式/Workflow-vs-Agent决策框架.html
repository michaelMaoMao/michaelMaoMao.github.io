Workflow vs Agent 决策框架

Workflow vs Agent 决策框架

这是得物活动搭建原文最有”可操作性”的一条经验，也是贯穿本系列的核心判断。

一、得物的判断法则（有限状态机法则）

流程能画成一张有限状态机图 → 用 Workflow
更像”给目标，让 AI 自己想办法达到” → 用 Agent
企业级多数是混合：大框架 Workflow 保可控，局部节点 Agent 提灵活

二、四篇/四场景实证（选型背后的理由）

场景 流程特征 选型 理由
得物·活动搭建 步骤明确、完成条件确定、正确率要求极高 Workflow (LangGraph) 可画成状态机
得物·数仓工作流 需求流转 + 规则资产化 + 经验沉淀 单 Agent + 多能力模块 (Hermes) 需自学习
得物·告警排查 ReAct 式查日志/指标/链路推理 ReAct Agent (Spring AI) 目标导向探索
高德·配图 召回/排序/质检同构批量 + 精排组合决策 Pipeline(重活) + Agent(巧活) 混合

三、决策 checklist

回答这 4 个问题：

  1. 流程步骤是否明确、完成条件是否确定？ 是 → Workflow 倾向 +
  2. 对正确率要求是否极高？ 是 → Workflow 倾向 +（可控）
  3. 是否需要”理解规则 + 组合决策”？ 是 → Agent 倾向 +（局部）
  4. 是否需要”给定目标自己探索路径”？ 是 → 纯 Agent 倾向 +
  • 1、2 都”是” → Workflow（大框架）
  • 3”是” → 在 Workflow 的局部节点用 Agent
  • 只有 4”是” → 考虑纯 Agent（但生产极少）

四、混合模式（大多数生产场景的最优解）

    subgraph WF["Workflow 大框架（可控）"]
        N1["节点1<br/>(代码/确定)"] --> N2["节点2<br/>(LLM 感知)"]
        N2 --> N3["节点3<br/>(Agent 局部推理)"]
        N3 --> N4["节点4<br/>(代码/确定)"]
    end

核心原则：路由权、计算权、校验权永远在代码；模型只做”感知 + 局部语义推理”。

五、行业旁证

  • Harrison Chase（LangChain 创始人）：大部分成功的 AI 应用是 Workflow 而非 Agent
  • Klarna 客服：被报道为”Agent”，架构上是精心设计的 Workflow（意图路由 + 工具调用 + 人工升级）
  • 真正在生产跑”完全自主 Agent”的案例极少

六、一句话

不要问”要不要用 Agent”，要问”我的流程能不能画成有限状态机”——能，就用 Workflow 把可控性握在手里，把 Agent 留给局部节点。
