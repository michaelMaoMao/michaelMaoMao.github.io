用 LLM Agent 重构告警排查流程｜得物技术

得物技术团队基于 LLM Agent 构建的告警自动排查系统 Troubleshooter，通过 ReAct 推理循环调度日志/指标/链路追踪工具，将中位数排查耗时从 20 分钟降至 4.4 分钟。本文梳理其架构、工具设计、幻觉控制与可观测性方案。

一、背景与痛点

传统告警排查的工作流程：

  • 第一反应是打开日志平台搜关键词
  • 切到 APM 看监控曲线
  • 再去链路追踪系统找 trace 详情
  • 三个平台来回切换，最后可能发现只是上游 GC 抖动导致的瞬间超时，一分钟后就自愈了

核心痛点：

  1. 耗时不在分析本身，而在频繁登录不同平台、拼凑分散的数据，单次告警排查通常需要 10～30 分钟
  2. 排查效率高度依赖个人经验，新人面对告警往往不知道该先看什么

于是得物团队做了 Troubleshooter——用 LLM Agent 自动完成告警的数据采集、根因分析和处置建议生成。上线后中位数排查耗时从 20 分钟左右降到 4.4 分钟，覆盖了 11 个服务和 10+ 种告警类型。

二、整体架构设计

分层解耦原则

整体采用分层设计，核心原则是告警接入与排查执行解耦：

  • 接入层：只负责接收和持久化告警
  • 排查层：由独立的调度器异步触发

技术栈与编排引擎选型

编排引擎：Spring AI Alibaba 的 ReactAgent（不是 LangGraph，也不是得物自研 Hermes）

选 Spring AI Alibaba 而非自建 ReAct 循环的原因是「省事」——框架已内置：

  • 推理循环
  • 工具拦截器（ToolInterceptor）
  • 模型拦截器（ModelInterceptor）

备注：得物另有一篇《从0到1搭建一个智能分析 OBS 埋点数据的 AI Agent｜得物技术》使用 obs-mcp-server 的 MCP 路线，与本篇的 Spring AI Alibaba 路线不同。本篇通篇未提及 Hermes 或 LangGraph。

三、核心流程（端到端排查链路）

完整排查链路分 7 步：

步骤 节点 说明
1 告警接入 接收告警数据，生成唯一事件 ID
2 指纹生成 提取 5 维度特征（服务名、告警类型、错误模式、指标名、错误摘要），生成 32 位 MD5 指纹
3 知识匹配 在知识库中检索相似记录，匹配成功则直接复用历史结论（秒级返回）
4 AI 排查 SupervisorAgent 编排排查，执行 ReAct 推理循环
5 结论验收 独立的 ValidationAgent 检查根因明确性和处置建议完整性
6 报告推送 生成 Markdown 格式报告，推送到飞书群组
7 知识沉淀 运维确认后的结论存入知识库

关键设计：指纹 + 知识匹配构成了已知问题的快速通道，AI 排查只针对新问题或匹配失败的场景，兼顾效率与成本。

四个排查工具的设计哲学

工具一：queryLogs —— 日志查询与分析

日志是排查的第一入口，通过 WebSocket 连接日志平台，按优先级分批查询：

  • 每批结果都经过 LLM 异步分析，最后汇总所有批次的结论
  • 日志去重（LogDeduplicator）：防止同一请求的多条日志重复占据分析窗口

工具二：queryMetrics —— 监控指标查询

支持 10 个维度的指标查询：qps, rt, errorRate, containerCpu, containerMemory, percentileRt, gcCount, gcRt, qpstop10, rttop10

LLM 可根据告警类型自主决定查询哪些维度：

  • OOM 告警 → LLM 通常选 qps,rt,containerCpu,containerMemory,gcCount,gcRt 全维度
  • 接口 RT 突增 → 关注 qps,rt,percentileRt,rttop10

MetricService 接口为不同环境（csprd/oa/pre/t1）提供可插拔实现，因为 APM 查询参数中环境代码不同——生产环境用 csprd-proxy，测试环境用 t1-proxy。

工具三：queryTrace —— 分布式链路追踪

当告警带有 traceId 时，直接查询 APM 获取 Span 树，渲染为格式化文本后交给 LLM 分析，能识别出哪个下游依赖变慢、哪个环节抛出了异常。

工具四：queryEndpointErrors —— 接口错误排查

当没有 traceId 但有明确的接口路径时，查询该接口的错误日志，通过正则提取所有 traceId，再逐个分析。

重要防护逻辑：当 endpoint 为根路径 / 时拒绝执行——匹配所有请求的查询不具备排查意义。

五、上下文与策略管理

动态策略组装（Prompt 模板）

不同服务、不同告警类型的排查思路差异很大：

  • OOM 告警 → 关注 GC 指标和堆内存
  • 接口超时 → 关注 QPS 突变和下游依赖延迟

设计了策略匹配机制：按 (service_name, alert_type) 从数据库精确匹配排查策略，未匹配时使用内置兜底策略。

运维人员可通过前端页面在线编辑策略内容，无需改代码——这是低代码运维的关键设计。

工具超时隔离

外部系统（日志平台、APM）不一定稳定。每个工具调用通过 ToolExecutor 包装，用独立线程池 + Future.get(timeout) 实现超时控制：

降级策略：超时时返回降级消息（如「指标查询超时，继续使用已有信息进行排查」），LLM 会基于已有证据继续推进，不会因单个工具超时导致整个排查流程中断。

上下文窗口管理

文章未明确提及大上下文压缩机制（如滑动窗口、摘要压缩），但通过以下设计间接控制上下文膨胀：

  • 日志去重（LogDeduplicator）：防止同一请求的多条日志重复占据分析窗口
  • 分批查询 + 每批 LLM 异步分析 + 汇总：避免一次性灌入全量日志
  • 工具返回「分析摘要」而非原始数据（如 queryLogs 返回「排查摘要」而非原始日志文本）
  • 环境字段不让 LLM 自行映射：在 tool 方法中直接使用告警事件中的环境字段，避免 LLM “翻译” 环境名时出错

六、幻觉控制与结论质量保障

LLM 输出不稳定是落地最大的风险点。从四个维度构建幻觉控制体系：

维度 机制 说明
规则格式校验 零 LLM 调用 第一轮检查 5 个必要章节是否存在、指标表格格式是否规范，毫秒级完成
独立验收 Agent 内容质量审查 检查：结论是否明确、核心判定是否合理、根因是否有工具证据、建议是否可执行
多轮交叉验证 工具结果相互印证 queryLogs × queryTrace、queryLogs × queryMetrics、时间线一致性校验
重试机制 分级重试 格式问题不消耗重试配额；内容问题最多重试 2 次；验收 Agent 异常时宽容通过

八、真实排查案例：效率网关超时

以一次生产环境网关超时告警为例：

告警信息：

AI 排查过程：SupervisorAgent 在 4 分钟内完成了 3 次工具调用 + 1 轮验收修正：

  • 第 1 次验收（未通过）：缺失必填字段，要求补全
  • 第 2 次验收（通过）：LLM 补充了结构化字段，紧急程度为「观察」，置信度为「高」

AI 最终排查结论（节选）：

本次告警系舆情管理端服务底层 gorm-v2 数据库查询严重阻塞，引发效率网关 30 秒硬性超时，经排查确认为特定多条件过滤场景下的偶发性慢查询导致的链路中断。

根因：upgrade_quality_status IN (0,1,2,3,5) 多条件过滤 + 分页查询时，底层 gorm-v2 数据库组件执行严重阻塞，耗时 29.99s，超过效率网关 30s 超时阈值，触发 TimeoutException。

置信度：高（分布式调用链完整还原了 99% 耗时集中于 gorm-v2 组件，网关超时堆栈、响应式流中断机制与业务端多状态过滤 SQL 高度吻合）

效果对比：整个排查过程从告警接入到输出结论耗时约 4 分钟（工具调用总计 88s + LLM 推理 + 验收）。人工排查保守估计需 10～20 分钟。

环境统一映射

十一、后续迭代方向

按优先级规划：

  1. 多 Agent 并行排查：日志查询和指标查询可以并行执行
  2. 指纹知识库：实现秒级匹配已知问题
  3. 跨服务关联分析：识别级联故障
  4. 自动处置能力：从「排查 + 建议」升级到「排查 + 自动修复」
  5. 向量语义检索：实现语义级相似问题检索

可借鉴的设计模式

  1. 编排引擎选型务实：不盲目自研，用 Spring AI Alibaba 的开箱 ReactAgent 换开发效率
  2. 接入与执行解耦：接入层只持久化，调度器异步触发排查，避免阻塞告警链路
  3. 指纹 + 知识匹配：已知问题秒级复用历史结论，AI 只排查新问题，兼顾效率与成本
  4. 工具返回「分析摘要」而非原始数据：由工具侧用 LLM 预处理，避免主 Agent 上下文爆炸
  5. 动态策略组装：(service_name, alert_type) 匹配策略 + 运维低代码编辑，无需改代码即可适配新场景
  6. 工具超时隔离 + 降级消息：独立线程池 + Future 超时，单工具失败不阻断整条链路
  7. 分层幻觉控制：格式校验用代码（零 LLM、毫秒级）、内容校验用独立验收 Agent，避免「LLM 验 LLM」
  8. 交叉验证：多工具结果必须相互印证（日志×链路、日志×指标、时间线一致性）
  9. 验收循环 + 反馈注入重试：不通过时把验收反馈注入 prompt 让 LLM 修正，而非简单重试
  10. 文件系统可观测性：按事件 ID 分目录的完整调用日志，便于事后审计与 Debug
  11. 不让 LLM 做确定性映射：环境字段在 tool 方法中直接使用，避免 LLM 翻译出错
  12. Round-Robin 多 Key + 事件 ID 哈希固定：分散限流压力，同时保证同一会话上下文连续性
