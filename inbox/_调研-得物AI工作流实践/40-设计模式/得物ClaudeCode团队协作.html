得物 AI 编程实践：从 Claude Code 实践到团队协作的优化思考

得物商家域团队把 Claude Code 从”单兵工具”演进到”多子代理团队协作”的完整方法论沉淀。核心是把人类认知科学（工作记忆 7±2、渐进式知识构建）映射成对 AI 的结构化约束：精准对话流 / Plan 模式 / 系统提示词 / SKILL&MCP / 子代理协作五大能力，全部围绕”确定性机制锁定 + 模型只做语义感知”这一得物主线。

一、一句话定位

得物商家域团队基于 Claude Code 落地一套人机协作开发范式：用”精准对话流 + Plan 模式 + 系统提示词”驯服单 Agent 的注意力与约束衰减，用”SKILL/MCP”沉淀复用资产，再用”技术方案文档驱动的多子代理协作”把团队协作模式搬进 AI。所有方法的共同根基是认知科学——控制 AI 的认知负荷，与人类带新人的方法同构。

二、核心能力拆解

2.1 精准对话流设计：控制 AI 思考的艺术

定位：把人类编程思维转成 AI 可理解的结构化交互。Claude Code 像”热情但经验不足的实习生”——不给明确指令就给”惊喜”。

三个关键机制：

机制 含义 反面踩坑
上下文聚焦 单次对话只处理一个功能模块 曾在一个对话里同时处理多模块，AI 把两个模块的错误处理逻辑混在一起
约束明确化 用具体指令压缩 AI 自由度 不说”遵循项目规范”，而说”使用 ResultDTO 作统一返回格式，错误码参考 ErrorCodeEnum”
增量式提问 “先框架后细节”，先接口定义后实现 类似带新人”先搭骨架再填肉”

初始 prompt 必须明确的四件事：①功能边界与目标（做什么/不做什么）②技术约束与规范 ③输出格式与交付物 ④分阶段实现计划。

真实踩坑：AI 跨模块依赖时易”忘记”约束。技巧——每个新实现阶段开头简要回顾关键约束，例如”现在处理任务交接流程，请记得：1. 用 Redis 分布式锁；2. 需修改商运关系和新商成长任务；3. 异常处理符合规范”。

2.2 Plan 模式：复杂任务的系统化分解

借鉴项目管理 WBS（工作分解结构）。直接把”实现完整拜访任务系统”丢给 AI 会得到：逻辑不完整、模块接口不一致、技术选型不合适。

三步法：需求分析与模块划分 → 技术方案设计 → 任务优先级排序。

2.3 系统提示词（CLAUDE.md）：给 AI 立”规矩”

定位：相当于给新人的”入职手册”。但新手常犯错误是写成”百科全书”——得物早期系统提示词长达 5000 字塞进所有规范，AI 要么忽略要么顾此失彼，效果反而差。

关键反直觉结论：系统提示词应像”护栏”而非”详尽手册”，针对 AI 常见错误模式的针对性提示 >> 全面但泛泛的规范。得物现控制在 200 字以内。

三个关键模块结构（原文以图示展示模板，核心是分块而非全文堆砌）。

三条编写技巧：

  1. 避免信息过载：不塞所有知识，而是指引 AI 按需查文档。例：”遇到分布式事务问题时，参考 /doc/分布式事务最佳实践.md 的 TCC 模式”。
  2. 正向引导优于禁止：不说”不要用过时 API”，而说”请用 OrderServiceV2 替代 OrderServiceV1”。
  3. 动态调整：每两周回顾一次，针对 AI 近期常犯错误补约束。例：发现 AI 忘记处理空指针 → 新增”所有方法入参必须用 ValidateUtil.isEmpty() 非空校验，异常抛 IllegalArgumentException”。

2.4 SKILL 与 MCP：知识沉淀与外部能力扩展

SKILL 机制：把单次生效的 Prompt 沉淀为可反复调用的标准化复用资产。例：团队总结”ES 数据查询”内部 SDK 调用方式 → 封装成 SKILL → 后续类似场景直接调用即按最佳实践实现。

最适合封装 SKILL 的场景：

  • 复杂工具使用指南（ElasticSearch 接入、Redis 缓存更新策略）
  • 常见错误处理模板（分布式锁冲突处理、数据库乐观锁重试机制）

MCP 协议：解决 AI 与外部工具/数据源连接，让 AI 从静态知识升级到动态访问实时数据。得物集成了飞书 MCP 服务器，三个典型场景：

  1. 自动生成技术方案文档：AI 分析需求后调用 feishu_create_doc，直接在指定知识库目录创建格式化文档。
  2. 读取 PRD 需求：用户提供飞书文档链接 → feishu_get_doc_content 取内容 → 基于完整需求生成方案。
  3. 数据同步到多维表格：feishu_append_bitable_data 自动追加代码统计数据（行数、涉及文件），便于团队追踪 AI 编程效率指标。

三、结构化对话设计方法论（团队级标准流程）

3.1 传统”需求-响应”模式的失败根源：三个核心矛盾

矛盾 表现 例子
语义鸿沟 自然语言模糊 vs 代码精确 说”接口要安全”，AI 理解为”登录校验”，实际想要 @Permission 注解 + ValidatorUtil 校验 + 操作日志
约束衰减 对话推进中早期约束权重渐降 第1轮强调”必须继承 BaseServiceImpl”，第5轮 AI 忘记实现独立 Service，第10轮连分层架构都混淆
目标偏移 AI 过度关注细节忽视整体 纠结参数命名优雅，却漏掉分页、排序等必需功能

3.3 背后的认知科学原理

  • 工作记忆限制理论：人一次记 7±2 个信息块，AI 上下文理解同样有限 → 分阶段 + 单模块控制认知负荷。
  • 渐进式知识构建：先整体框架后细节，符合认知规律，与教新人”先架构图→模块交互→具体实现”同构。

四、AI 子代理协作模式（团队级核心创新）

4.1 为什么需要子代理：传统团队协作三大痛点

  • 信息传递损耗：需求文档经多环节传递，像”电话游戏”传到后面面目全非。
  • 责任边界模糊：出问题时”架构问题/实现问题/测试不充分”互相推诿。
  • 反馈周期漫长：需求到代码审查走几天，发现问题已投入大量资源。

4.2 核心机制：中间产物驱动（借鉴 MetaGPT）

所有子代理通过共享**”技术方案文档”**协作——这是团队的”共享白板”，含需求分析、模块划分、实现状态、接口设计。每个子代理只修改自己角色相关部分，确保一致性。

为什么选中间产物驱动而非直接沟通：直接对话导致沟通渠道指数级增长（n 个代理有 n(n-1)/2 渠道）。单一事实来源大幅降低协作复杂度，且便于追踪变更历史。

4.3 四个核心子代理角色

角色 对应现实角色 核心职责
技术方案架构师 架构师 需求拆解、模块划分、技术选型、接口定义、数据模型、依赖梳理、维护技术方案文档
代码审查专家 技术负责人 架构合规性、规范命名、潜在性能/bug、可维护性评估、具体修改建议
代码实现专家 主力开发 按方案实现代码、写单测集成测试、修复审查问题、写 API 文档、同步实现状态
前端页面生成器 前端（定制） 按接口定义生成符合低代码平台规范的前端页面配置（商家域管理后台定制角色）

角色划分依据：基于软件开发自然阶段（设计→实现→审查）+ 专业领域（后端→前端），符合 SDLC 自然规律，不盲目追求角色数量。

4.4 协作流程：”先整体规划，再迭代实现”（Sprint 规划 + Daily Scrum）

为什么增量迭代而非一次性开发：复杂系统构建本质是不断学习调整的过程，及早发现问题调整方向，避免错误道路走太远——即”小步快跑，快速迭代”。

4.5 子代理协作的三个显著价值

  1. 专业化分工提升质量：专门代码审查子代理比通用 AI 能发现更多潜在问题（类比专科医院 vs 综合医院）。
  2. 流程标准化降低风险：技术方案文档 + 明确角色分工，让流程标准化可视化，新人看文档即可上手。
  3. 知识沉淀促进复用：专业知识与决策逻辑编码为可复用配置规则，避免”人走经验丢”。

4.6 子代理协作的四个实际挑战与应对

挑战 应对
上下文同步问题（文档更新各代理未及时同步） 每次修改文档后明确通知相关代理”技术方案 XX 部分已更新”
协作边界模糊（跨模块功能该谁负责） 技术方案文档加”责任人”字段，明确每模块归属
灵活性与标准化平衡 原则：90% 常规严格遵循标准流程，10% 特殊情况人工介入
错误传递放大效应（方案设计错则后续全错） 加强技术方案人工评审，确保”地基”打牢

五、真实踩坑与人机协同要点

5.1 上下文管理四个实用技巧

  1. 对话线程化：不同功能模块用独立对话线程（曾在同一对话讨论三模块导致上下文混乱到推倒重来）。
  2. 关键信息锚定：重要技术决策和约束在对话中反复强调。
  3. 文档外化：复杂设计记录在外部文档而非依赖对话历史，对话中引用（”数据库设计详见 /doc/db_design.md，特别是索引设计部分”）。
  4. 状态可视化：技术方案文档用进度标记 [未开始]/[设计中]/[已实现]/[已审查] 直观跟踪。

5.2 质量控制三个关键策略

  • 多层次验证：单测（AI 生成）+ 集成测试（人工设计）+ 代码审查（人机结合）三层验证体系。
  • 渐进式信任：从简单低风险模块开始用 AI，先内部工具验证无误再用于核心业务。
  • 错误模式学习：维护”AI 错误案例库”，记录”忘记处理分布式锁超时””日期格式转换错误”等典型问题及解决方案，针对性优化系统提示词。

5.3 人机协作最佳平衡点：三类工作划分

  • AI 主导：标准化代码生成（基础 CRUD）、单测编写、API 文档生成等重复性高规则明确的任务。
  • 人机协作：技术方案设计、复杂逻辑实现、代码审查等需领域知识 + 创造性思维的任务。
  • 人类主导：需求分析、架构设计、质量决策等高风险高创造性任务。

核心定位：”人类主导，AI 辅助”——而非反过来。开发者对 AI 生成代码负全部责任，如同对自己写的代码负责。

六、AI 编程的局限性认知（清醒边界）

  1. 创造性思维不足：AI 擅长已有知识范围内组合优化，突破性创新有限。尝试让 AI 设计全新商家结算模型时，仍倾向参考现有模型修改，难跳出框架。
  2. 上下文理解深度有限：即便上下文窗口很大，对”牵一发而动全身”的核心模块仍难把握深层设计意图与隐性依赖。
  3. 质量责任边界模糊：AI 代码出质量问题时责任界定复杂——得物解法是开发者负全责。
  4. 领域知识滞后性：AI 对公司内部系统最新变更反应不及时——得物建立”知识库更新机制”，每月整理最新系统变更和业务规则成文档供 AI 参考。

七、可借鉴点与已挖研究的关系

7.1 与 id=213（多 Agent 主从架构）的呼应

维度 id=213 Claude Code 工作流 id=202 团队协作（本文）

互补关系：id=213 侧重工具层选型与成本（模型插拔、Shell 别名、多屏布局），id=202 侧重方法论与团队协作范式（对话流、Plan、子代理协作）。两者拼起来是得物 Claude Code 实践的完整图景：工具选型 → 单兵方法论 → 团队协作范式。

7.2 与你环境的强同源（skill 系统 / MCP）

  1. SKILL 同源：本文的 SKILL 机制（把 Prompt 沉淀为可复用组件，如 ES 接入、Redis 缓存策略封装）正是你 ~/.claude/skills/ 体系（auto-skill/web-access/flow-deep 等）的同一思想。得物的”复杂工具使用指南””常见错误处理模板”封装为 SKILL，对应你的 skill-creator 与 gsd 系列经验沉淀。
  2. MCP 同源：得物集成飞书 MCP（feishu_create_doc / feishu_get_doc_content / feishu_append_bitable_data）扩展 AI 外部能力，正是你 MCP.md 中 Context7/Sequential/Magic/Playwright 多服务器编排的同类实践。飞书 MCP = 你的 Hermes MCP（通知/同步/cron）的得物版本。
  3. 三阶段对话模型 ≈ flow-deep 管道：需求定义（Stage 1 Prompt 优化）→ 边界明确（Stage 3 规划）→ 迭代反馈（Stage 4 执行 + Stage 5 验证），结构高度同构。
  4. 子代理中间产物驱动 ≈ planning-with-files：技术方案文档作单一事实来源 = planning-with-files 的 task_plan.md/findings.md/progress.md 契约化文档。
  5. 系统提示词 200 字护栏：与你 CLAUDE.md 的”3S 原则（Single/Specific/Short）”和 RTK token 优化理念完全一致——信息过载反伤效果。

7.3 可直接迁移的实践

  1. “约束衰减”对抗技巧：每个新实现阶段开头回顾关键约束——可固化进 flow-deep 的 Stage 4 执行模板。
  2. 系统提示词动态调整：每两周回顾 + 维护”AI 错误案例库”——可建立定期 review 机制。
  3. 子代理”责任人”字段：在 planning-with-files 的 task_plan.md 中为每个任务标注负责的子代理/Agent 类型，解决协作边界模糊。
  4. 90/10 原则：90% 常规走标准流程，10% 特殊人工介入——作为 multi-agent 编排的兜底策略。
  5. 领域知识月更机制：定期把内部系统变更整理成文档供 AI 参考——对抗 AI 领域知识滞后。

九、一句话总结

得物把”带新人”的认知科学（工作记忆 7±2、渐进式构建、护栏而非手册）系统化映射成对 Claude Code 的五层约束（对话流/Plan/提示词/SKILL&MCP/子代理），再用”技术方案文档作单一事实来源”把人类团队协作范式搬进 AI——核心仍是得物一以贯之的”确定性机制锁定 + 模型只做语义感知”，与你 flow-deep + planning-with-files + skill 体系高度同源。
